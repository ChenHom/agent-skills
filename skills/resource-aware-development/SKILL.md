# Resource-Aware Development

善用現有的運算、記憶體、網路、時間與預算，在滿足需求、安全、可靠性與可維護性的前提下消除浪費。資源利用率不是目的，應以符合需求的整體效益為準。

## 適用範圍

- 功能開發或設計：依預期工作負載及風險考慮資源消耗。
- 既有系統的效能、容量或成本問題：以量測與瓶頸分析決定改善方式。
- 純文字或低風險的小改動：沿用一般工作流程，不強制建立基準、效能測試或額外產物。

本 skill 補充既有開發、安全及測試規範，不取代它們；不以 CPU 滿載、零依賴或單機為固定目標。

## 日常功能開發

1. 明確需求、預期負載、資源限制與完成標準；未知數影響設計時先查證，無法查證則記下假設。
2. 檢查既有程式、標準函式庫及成熟工具，選擇足夠簡單且可維護的方案；依賴的安全、相容與維護成本也要納入。
3. 依工作負載留意資料量、資料搬移、重複查詢、記憶體峰值、網路與外部服務呼叫。大資料可考慮分批或串流；不要只因可能成長便預建分散式架構。
4. 按風險選擇驗證：資源敏感功能使用具有代表性的資料及條件量測；一般小改動執行相稱的功能檢查即可。

## 有明確效能、容量或成本問題時

1. 定義目標與情境，建立可重現的基準；視情況記錄負載、資料規模、環境、延遲、吞吐量、記憶體或費用。
2. 根據 profile、指標、追蹤或查詢計畫找瓶頸；不要把猜測當結論。無法量測時說明限制與未確認事項。
3. 比較演算法、查詢、資料處理、設定、服務及擴容方案的效果、風險和總成本。必要的冗餘與容量餘裕也是需求。
4. 小步修改，依可比較的條件量測前後差異，驗證正確性與可靠性；未經驗證不得宣稱改善。
5. 達標或進一步改善的代價高於效益時停止；簡要記錄數據、取捨及剩餘問題。

遇到正在發生的故障或服務中斷，允許先採取已授權的擴容或其他止血措施，再補量測及根因分析；不要為等待完整基準延誤必要處置。

## 邊界與例子

- 安全、正確性、必要備援和可維護性不可為追求效能而犧牲；不自行實作密碼學來減少依賴。
- 大型 CSV 匯出：先了解資料規模；有大量資料的合理預期時考慮分批讀取、串流輸出，並用代表性資料檢查時間及記憶體。
- 查詢變慢：先看延遲、負載與查詢計畫，再決定修改查詢、索引或擴容；不要預設是哪一層出問題。
- 系統已達標但要求 CPU 常態 100%：先評估尖峰餘裕、延遲和可靠性；利用率本身不是成功標準。

## 回報

依任務規模簡述目標、方案與資源取捨；若有明確效能或成本目標，附量測條件、前後數據、驗證結果及尚未確認的事項。
