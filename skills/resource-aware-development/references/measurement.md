# 量測工具與 AI 成本

先確認專案實際的技術棧、版本、權限與現有觀測方式，以下僅為可選範例，並非對特定專案環境的宣稱。使用既有唯讀資料優先；新增監控、計費資源或改動正式環境需符合既有授權。任何量測應記錄時間範圍、環境、負載與資料規模。

## HTTP 與 Nginx

- 已有 access log 時，依 route、狀態碼與時間區間比較請求數、錯誤率及 p50／p95／p99 延遲。Nginx `$request_time` 為請求總時間，包含接收請求及回傳客戶端資料；`$upstream_response_time` 為上游回應時間，可能有多個上游值，不能直接當作單一應用執行時間。
- 僅在既有 log format 有這些欄位時使用；缺欄位應先說明，修改 log format 或重新載入服務需遵守正式環境變更規則。避免輸出 URL 查詢參數、個資或憑證。

## MySQL

- 先確認版本與 SQL 類型；可先看 `EXPLAIN`，支援時以代表性參數檢查 `EXPLAIN ANALYZE SELECT ...` 的實際列數、耗時及索引使用。
- `EXPLAIN ANALYZE` 會執行查詢，不是純計畫預覽；先評估負載、鎖定與權限，優先在隔離環境或低風險時段執行，不對未知 SQL 或正式資料直接測試。

## CloudWatch

- 若已使用 AWS，先讀現有 CloudWatch Metrics 與 Logs Insights，依服務及維度比較請求量、錯誤、延遲與資源用量；確認時間範圍、統計方式及單位。Logs Insights 掃描資料可能產生費用，限制時間範圍與 log group。
- Metric filter 用來從日誌產生指標，並非直接量測所有系統的工具。只有確定日誌缺少所需指標且有權限及必要性時才提議新增；新 filter 只處理建立後的日誌，不能補出歷史數據，並需考量費用及敏感資訊。

## AI 用量與成本

1. 用供應商 usage、billing 或既有追蹤，依模型及任務記錄請求次數、輸入／輸出 token、快取讀取／寫入 token（若有）、失敗與重試、延遲、成功數與計費期間。各供應商分類不同，避免重複計算已包含在 input 中的 cached tokens。
2. 以計費期間適用價格計算分項成本，並對帳實際帳單；記錄幣別、單價與折扣。每次請求成本 = 可歸屬成本 ÷ 請求數；每個成功任務成本 = 總成本（含重試）÷ 成功任務數；分母為零時標示不可計算。
3. 應用層快取命中率 = 命中次數 ÷ 快取查詢次數；供應商提示快取使用不同口徑，可另報 cached input tokens ÷ total input tokens（僅當前者是後者子集）。不可混稱或由 token 比例推算請求命中率；缺資料標示未知。
4. 以代表性任務及相同品質標準比較模型路由、上下文長度與快取策略。記錄品質、延遲、錯誤率及單位成本；注意敏感資料和快取失效。只有品質符合需求才部署或建議切換。
